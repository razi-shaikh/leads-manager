2. System Boundaries and Data Flow

Browser (login, dashboard, all-leads, pipeline pages)
  │  Server Actions / fetch to Route Handlers (same Next.js app)
  ▼
[Auth guard]  requireSession() — every protected action/route/page.
  │  Rejects unauthenticated requests before any business logic.
  ▼
[Service layer]  server-only modules — the ONLY code importing the DB client.
  │  Leads, notes, history, import, photos, dashboard stats.
  ▼
[Neon Postgres]  tables: leads, lead_notes, lead_events
  │
  ├──► [Frappe upload_file]  server-side photo uploads only (scope: Home/LeadManager)

CSV photos: used as remote URLs directly in the carousel (see open decision O2).

4. Trust Boundaries and Authorization

  • Boundary 1 — browser vs server: all auth checks run server-side (middleware + requireSession()). UI hiding is never the enforcement.
  • Boundary 2 — server vs secrets: Frappe token, DB URL, and login credentials live in env vars; none is ever sent to the browser or logged.
  • Single-user model: authentication (logged in?) is the only gate; there are no roles, orgs, or per-record permissions in MVP.

5. Error Handling and Logging Strategy

  • Server actions/handlers return typed results ({ ok, data | error }); unexpected exceptions are caught, logged server-side, and shown to the user as a generic message.
  • Client shows failures via error toasts with a retry path; empty states explain the next action.
  • LOGGED: action name, lead id, timestamp, error code/message. NEVER LOGGED: passwords, tokens, session cookies, customer phone/email contents, stack traces to the client.

6. Persistence and Migration Strategy

  • Schema defined in Drizzle; migrations generated with Drizzle Kit and committed to the repo.
  • Tables (proposed): leads (all CSV + card fields, status enum, source, duplicate flag, photo URL list, timestamps), lead_notes (lead id, text, created_at), lead_events (lead id, type=status_change|note|edit|import, from/to, created_at) powering the history timeline.
  • Status stored as a Postgres enum of the six values; transitions are unrestricted in MVP (any status from the dropdown).
  • Dev safety: use a Neon branch database for local development; production branch only from Vercel prod env.

7. Deployment

  • Environments: local dev (Neon branch DB) → Vercel preview (per PR, branch DB) → Vercel production (production DB).
  • CI/CD: Vercel Git integration; every push builds (tsc --noEmit, ESLint, next build) before deploy.
  • Env vars per environment: DATABASE_URL, APP_USERNAME, APP_PASSWORD_HASH, SESSION_SECRET, FRAPPE_UPLOAD_URL, FRAPPE_API_KEY, FRAPPE_API_SECRET.
