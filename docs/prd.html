Product Requirements — Bike Purchase Leads Management System (MVP)

Project: F3 Motor  |  Version: Draft for review  |  Date: 2026-10-17
Source: Phase 1 planning discussion. No code exists for these features yet.

1. Problem Statement

F3 Motor receives bike-purchase leads from multiple sources — its own website (BikeBecho.com), Bike4Sale, and Facebook. Today there is no single system to collect, view, qualify, follow up on, and close these leads. The result is scattered lead data and no consistent workflow from first contact to final outcome.

2. Target User

A single internal F3 Motor user who imports leads daily and works them end to end. MVP has one login only; no multi-user accounts and no roles.

3. Core User Journeys

J1 — Daily lead import

  1. User logs in with the single set of credentials.
  2. User uploads a CSV file of new leads.
  3. System creates every row as a lead with status New Lead, tagging rows whose Phone + Registration No. already exist as duplicates (still created, never skipped).
  4. User sees the new leads on the Dashboard counts and in All Leads.

J2 — Morning triage

  1. User opens the Dashboard and sees total counts grouped by status plus how many new leads arrived today, optionally filtered by lead source.
  2. User opens All Leads, scans the new cards (photo carousel, bike details, price, contact), and uses search (name, phone, reg no.) and filters (status, source) to find specific leads.

J3 — Qualify and follow up

  1. From All Leads or Pipeline, user changes a promising lead's status from the card dropdown (New Lead → Qualified → Follow-up). Not all leads are qualified.
  2. In Follow-up, user contacts the customer and records notes (plain text with timestamps).

J4 — Negotiate and close

  1. User moves the lead to Negotiation, then to a final outcome: Closed Won or Closed Lost.
  2. User opens View History to see the full timeline of status changes and notes.

J5 — Lead maintenance

  1. User edits any field of a lead when details change.
  2. User deletes leads that should not be kept.
  3. User uploads additional bike photos to a lead when needed.

4. Functional Requirements

Each requirement is written as a testable behavior.

Authentication (FR-A)

IDBehavior
FR-A1When valid credentials are submitted on the login page, the system grants access to all pages.
FR-A2When invalid credentials are submitted, the system denies access and shows an error without revealing which part was wrong.
FR-A3When an unauthenticated visitor requests any page except login, the system redirects to login.
FR-A4The username and password are read from environment variables; no credential appears in source code.

CSV Import (FR-I)

IDBehavior
FR-I1When a CSV is uploaded, the system creates one lead per row from whichever recognized columns are present (all columns optional; missing fields stay blank), each with status New Lead.
FR-I2When a row's Phone + Registration No. matches an existing lead, the system still creates the lead and tags it as a duplicate.
FR-I3When the upload finishes, the system reports how many leads were created and how many were tagged as duplicates.
FR-I4When a CSV has no recognized columns, is unreadable, or has malformed rows, the system rejects it with a clear error and creates nothing.

Recognized CSV columns (all optional, any order; unknown columns ignored): ID, Lead Source, Date, Customer Name, Phone, Email, Brand & Model, Reg No., Year, Bike Photo (Multiple photos), KM Driven, No. of Owners, Location, Expected Price.

Dashboard (FR-D)

IDBehavior
FR-D1When the Dashboard loads, it shows the total lead count grouped by each of the six statuses.
FR-D2When the Dashboard loads, it shows how many new leads were added today.
FR-D3When the user picks a lead source filter (BikeBecho.com, Bike4Sale, Facebook, or All), all counts update to that scope.

All Leads (FR-L)

IDBehavior
FR-L1When All Leads loads, it displays leads as cards, 50 per page, with pagination controls.
FR-L2When the user types in the search box, results narrow to leads matching name, phone, or registration no.
FR-L3When the user sets the status filter, only leads with that status are shown.
FR-L4When the user sets the source filter, only leads from that source are shown.
FR-L5Only card view exists in MVP; no table view.

Pipeline (FR-P)

IDBehavior
FR-P1When the Pipeline page loads, it shows status tabs for Qualified, Follow-up, Negotiation, Closed Won, and Closed Lost (no New Lead tab).
FR-P2When the Pipeline page loads, the Qualified tab is selected by default.
FR-P3When the user clicks a status tab, the page shows that status's leads as cards with the same search, filters (source), and pagination (50/page) as All Leads.

Lead Card and Actions (FR-C)

IDBehavior
FR-C1Every card shows an image carousel at the top, then brand & model, registration no., year, KM driven, owners, location, expected price, customer name, phone, and email.
FR-C2Every card shows a color-coded status tag for its current status.
FR-C3When the user picks a new status from the card dropdown (on any page), the lead's status updates immediately and the change is recorded in history.
FR-C4When the user edits a lead, every field is editable and changes persist.
FR-C5When the user confirms deletion, the lead and its notes/history are removed.

Notes and History (FR-N)

IDBehavior
FR-N1When the user adds a note, it is stored as plain text with a timestamp.
FR-N2When the user opens View History, they see a timeline of all status changes and notes in chronological order.

Photos (FR-M)

IDBehavior
FR-M1When a CSV row contains photo URLs, the card carousel displays those photos.
FR-M2When the user uploads photo files to a lead, the files are stored via the Frappe upload API and appear in the carousel.
FR-M3The Frappe API token is read from environment variables; it never appears in source code or client-side bundles.

5. Non-Functional Requirements

IDRequirement
NFR-1Performance: lead list pages render 50 cards per page without perceptible lag on a normal broadband connection.
NFR-2Reliability: a failed CSV import or photo upload leaves no partial lead data and reports the failure clearly.
NFR-3Privacy: customer phone numbers and emails are visible only to the logged-in user; they are never logged or exposed in URLs.
NFR-4Usability: the interface is clean, minimal, and professional; core flows (import → triage → status change → note) need no training beyond a walkthrough.
NFR-5Portability: all configuration that varies by environment (credentials, tokens, database URL) comes from environment variables.

7. Observable Success Measures

  1. Existing CSV leads import successfully and are viewable as cards with correct details and photos.
  2. The single user can run the system daily end to end: import → triage → qualify → follow up → close, with notes and history.
  3. Every lead can move through New Lead → Qualified → Follow-up → Negotiation → Closed Won / Closed Lost from the card dropdown on any page.

8. Acceptance Criteria — First End-to-End Outcome

  1. User logs in with the env-var credentials.
  2. User uploads the sample CSV; all rows appear as New Lead cards with correct data and duplicate tags where applicable.
  3. Dashboard shows correct per-status counts and today's new-lead count.
  4. User moves one lead through every status to Closed Won from card dropdowns; each change appears in that lead's history with notes added along the way.
  5. User edits a field, uploads a photo, and deletes a test lead successfully.
